## GrandTour: what is now established

Source object `7c7b7884e06a2082ac11f7b8a2ef3b7d25de5062` is the Git **tree object** returned by the official repository tree API, not a verified commit ID. Source snapshots are private and individually hashed in receipts 07–08. HF dataset revision remains `daf91c5e2b6db564822a35cc58222d73f8e75bab`.

1. **Intended corrected timestamp is explicit.** The [author paper §§3.2.1–3.2.3](https://arxiv.org/html/2602.18164v1) says the HDR stamp denotes the middle-row exposure midpoint. [`hdr_timestamp_adjuster.py`](https://github.com/leggedrobotics/grand_tour_box/blob/7c7b7884e06a2082ac11f7b8a2ef3b7d25de5062/box_utils/box_auto/python/box_auto/scripts/camera/hdr_timestamp_adjuster.py) pairs the image's V4L2 stamp with kernel trigger stamps and writes `msg.header.stamp = kernel_stamp + int((40+640)/(30*1400)*1e9 + 5.5e6)`, i.e. approximately 21,690,476 ns. The original bag write time is preserved, so header and bag times are not interchangeable. Default execution performs the update; an explicit `--skip_update` path only copies images. This is timestamp re-anchoring, not RS image rectification.
2. **An upstream processing dependency is documented.** [`kleinkram.yaml`](https://github.com/leggedrobotics/grand_tour_box/blob/7c7b7884e06a2082ac11f7b8a2ef3b7d25de5062/box_utils/box_auto/compose/kleinkram.yaml) declares the camera-calibration task dependent on successful HDR timestamp adjustment. The [official postprocessing wiki](https://github.com/leggedrobotics/grand_tour_box/wiki/General-%E2%80%90-Post-Processing) lists the correction. However the YAML comments name `_updated` inputs, while current [`update_calibration.py`](https://github.com/leggedrobotics/grand_tour_box/blob/7c7b7884e06a2082ac11f7b8a2ef3b7d25de5062/box_utils/box_auto/python/box_auto/scripts/calibration/update_calibration.py) actually consumes HDR `_encoding` bags and exports `_calib` bags; HF consumes renamed public `*_hdr_front.bag`. Thus there is evidence of intended ordering, not a complete hash-bound execution lineage for the published TAR.
3. **HF conversion preserves the header and does not explain 10 Hz.** [`message_parsing.py`](https://github.com/leggedrobotics/grand_tour_box/blob/7c7b7884e06a2082ac11f7b8a2ef3b7d25de5062/box_utils/box_converter/huggingface-dataset-conversion/dataset_builder/message_parsing.py) exports `header.stamp.to_sec()` and `header.seq`. [`build_data.py`](https://github.com/leggedrobotics/grand_tour_box/blob/7c7b7884e06a2082ac11f7b8a2ef3b7d25de5062/box_utils/box_converter/huggingface-dataset-conversion/dataset_builder/build_data.py) enumerates all messages; its only observed limiting option truncates a prefix via `max_messages`, default -1. No 30-to-10 decimator was found here. [`grandtour_release.yaml`](https://github.com/leggedrobotics/grand_tour_box/blob/7c7b7884e06a2082ac11f7b8a2ef3b7d25de5062/box_utils/box_converter/huggingface-dataset-conversion/configs/grandtour_release.yaml) says 10 Hz in descriptive prose, while the paper and [TierIV timing wiki](https://github.com/leggedrobotics/grand_tour_box/wiki/Sensors-%E2%80%90-TierIV-C1) give 30 Hz capture/line-clock information. Frame trigger cadence and row clock need not be identical; **neither actual released cadence nor downsampling is established**. Do not replace the vendor row interval with `1/(published_fps*height)`.
4. **No public processing receipt located.** The [converter entry point](https://github.com/leggedrobotics/grand_tour_box/blob/7c7b7884e06a2082ac11f7b8a2ef3b7d25de5062/box_utils/box_converter/huggingface-dataset-conversion/dataset_builder/__main__.py) creates `generation_report.txt` locally but uploads only `.zgroup`, YAML and TAR files. That makes the author's published timestamp semantics the available reference contract; it does not prove the exact source version/flags executed per HF mission. Adding the ~21.69 ms correction again to HF stamps would therefore be unjustified and risks double correction. A future protocol could explicitly adopt the author's midpoint contract, recording this residual provenance limitation, rather than pretend it was independently revalidated.

## Available IMU input distinct from the reference generator

The HF mission metadata already inspected lists `adis_imu.tar` (9,789,440 B) and `alphasense_imu.tar` (9,891,840 B), alongside the separate `cpt7_imu.tar` and `cpt7_ie_tc_odometry.tar`. The release config identifies ADIS16475-2 at 200 Hz and Alphasense BMI085 at 200 Hz, with distinct source topics and frame names. These are real alternative inertial instruments, not derivatives of the pose output.

The paper's Inertial Explorer reference uses CPT7 GNSS and its HG4930 IMU. Its Holistic Fusion route additionally uses total-station observations; the named HF `cpt7_ie_tc_odometry` is specifically the IE tightly coupled output, not a promise that Holistic Fusion is exported. [`update_imu_intrinsics.py`](https://github.com/leggedrobotics/grand_tour_box/blob/7c7b7884e06a2082ac11f7b8a2ef3b7d25de5062/box_utils/box_auto/python/box_auto/scripts/calibration/update_imu_intrinsics.py) loads per-sensor Allan-variance calibrations, fills acceleration/gyro covariance fields, and passes ADIS/BMI085 measurement values through unchanged. Only the STIM branch adds a mission-specific time shift. No pose-derived ADIS/BMI085 correction appears in this inspected processor. This supports **sensor/provenance separation**, not mathematical statistical independence: clocks share the CPT7 PTP reference, sensors share the rig, and calibration errors can be correlated. CPT7/HG4930 itself should not be represented as GT-independent input. No sensor-value validation has been performed.

**GrandTour decision:** strong conditional resource feasibility, with a declared author midpoint-timestamp contract and separate ADIS/BMI085 input option; 10/30 Hz publication discrepancy and exact per-mission execution lineage remain unresolved. Stop source expansion here. No scientific acquisition authorized by this note.

## Separately requested TUM-RS grayscale possibility

This is a prospective change of modality scope, before any new outcome: monochrome repeated identically into three channels for every RGB-network method tests grayscale-domain generalization. It creates no color information and must not be called a second RGB source. TUM capture is independent of GrandTour; ten trajectories do not imply ten independent laboratories or scene domains.

The [official TUM-RS page](https://cvg.cit.tum.de/data/datasets/rolling-shutter-dataset) provides synchronized GS/RS/IMU and poses, explicitly states IMU-frame GT, camera–IMU calibration, first-row exposure-midpoint image stamps, and manufacturer-derived approximate row delay 29.4737 microseconds. The [official directory README](https://cdn3.vision.in.tum.de/rolling/README.txt) says calibrated releases correct IMU axes/scale/constant bias and filter/align the mocap GT, including temporal alignment using differentiated orientation versus gyro. This is external optical pose evidence with a shared calibration procedure, not perfect statistical independence. It recommends the equidistant camera model; any resizing/remapping must retain each feature's original sensor-row time. Merely applying a pinhole model to distorted raw pixels would violate the geometry contract.

Public [EuRoC-format directory metadata](https://cdn3.vision.in.tum.de/rolling/exported/euroc/) is accessible without login. HEAD-only checks give seq1 1,847,756,800 B; seq4 1,719,214,080 B; seq2 1,214,996,480 B, all with `Accept-Ranges: bytes`. The seq2 figure is a **size feasibility example only, not a chosen evaluation sequence**. Combining its full TAR with the earlier GrandTour HDR/reference/TF/metadata example totals 2,284,584,567 B, or 2,294,374,007 B including ADIS: under approximately 2.43 GB before other overhead. This avoids relying on an untested selective TAR reader, but one sequence per source would provide limited coverage; no allocation is made. No 206/member access has been attempted by the direct HTTP client.

No explicit data license was found in the official TUM-RS page, top-level README or inspected directory listings. The TUM-VI project's license cannot automatically be transferred to this separate data collection. This is an unresolved published-terms contract, not a declaration that use is unlawful. Hence TUM-RS is technically credible as a second **grayscale** source if that modality is prospectively fixed, while license confirmation and the precise evaluation subset remain open.
